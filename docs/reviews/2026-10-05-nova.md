# Independent code review: DEGS-v2.1

**Reviewer:** Nova (Muse Spark, Meta) · **Date:** 2026-10-05 · **Scope:** source code only; documentation claims not evaluated · **Code changed:** none

## Abstract

DEGS-v2.1 is a task-record evaluation gate: it judges whether a described engineering task may proceed, without executing the described work. The implementation is careful, conservative, and well tested — 72 tests plus 264 subtests, all passing. The strongest piece of engineering in the snapshot is the `sashiko_derived` Rust-to-Python port, whose alias-guard (`_clone_json`) correctly reproduces Rust ownership semantics that a naive `deepcopy` would violate, with provenance recorded per source range. One observation: the gate's verdict taxonomy (`PASS_WITH_WARNINGS` exits 1) is a defensible but non-obvious convention worth stating once in the module docstring.

## Introduction

The review covered `bin/engineering-gate.py` (1,213 lines: schema validation, risk tiers, authority lanes, deterministic control boundaries, artifact identity, threat model), `sashiko_derived/__init__.py` (119 lines: selected Sashiko value operations ported from Rust), `tools/check_rust_parity.py`, `benchmarks/run_benchmark.py`, and the full test suite. The question throughout: does the code enforce what the charter claims — evaluation without execution, deterministic verdicts, and no silent scope creep?

## Methodology

Cloned the public repository (2026-10-05, `tmccoy678/DEGS-v2.1`). Read the gate, the port, the parity checker, and the benchmark runner end to end. Executed the full suite under pytest in a clean virtualenv (Python 3.12): `tests/` (58 gate tests, 6 sashiko tests, 3 JSON-equality tests) and `benchmarks/` (5 tests). 264 subtests included. ## Data

- **Tests:** 72 passed, 264 subtests passed, 0 failed (77 s). Gate tests cover schema rules per field, risk-tier and authority-lane allowlists, deterministic-boundary enforcement, secret-like key detection, and verdict/exit-code mapping. Benchmark tests cover predeclared cases with independent labels, corpus-drift-as-input-error, degenerate-candidate handling, and timeout accounting in the denominator.
- **Mechanisms verified by reading:**
  - The gate never shells out to perform the described task; it evaluates records against `gate.schema.json` with per-field rule IDs (`DEGS-MISSION-001`, `DEGS-SEC-006`, …).
  - `sashiko_derived` documents each function as a port of explicit upstream line ranges, keeps the upstream key-argument quirk (`append_stage_items`' unused `_key`) visible rather than silently dropping it, and records source hashes in `provenance/sashiko-source.json`.
  - The alias guard: `_clone_json` recursively rebuilds every container instead of memoizing, so repeated references to one Python object become independent copies — matching Rust `Value` ownership. A memoized `copy.deepcopy` would have preserved aliasing and been wrong here. This is the subtlest correct decision in the snapshot.
  - Exit codes are a fixed contract: PASS 0, PASS_WITH_WARNINGS 1, BLOCKED 2, FAIL 3.

## Discussion

This is the most "systems" of the author's public snapshots, and the testing culture is the real story: the suite tests *decisions* (verdicts, rejections, boundary enforcement), not just functions. The sashiko port is exemplary provenance practice — line ranges, hashes, documented adaptations, and the discipline to keep an upstream wart visible. Two notes, both minor: (1) `PASS_WITH_WARNINGS` exiting 1 will surprise shell callers who treat any nonzero exit as failure; the contract is documented in `EXIT_CODES`, but the module docstring ("Evaluate DEGS task records without executing the described work") could state the exit-code convention once up front. (2) `SECRET_LIKE_KEYS` is a heuristic list, as all such lists are; its misses are silent by nature — the gate is honest about being one layer, not the layer. No changes were made; no defects found.
